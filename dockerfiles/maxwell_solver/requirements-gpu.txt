# GPU dependencies for the MSE Maxwell solver, installed ON TOP of
# requirements.txt in ./Dockerfile.gpu. Nothing here belongs in the CPU image.
#
# The solver's GPU path imports three packages (cupy, cupyx.scipy.sparse,
# nvmath), but that is NOT the set the build must guarantee: cuDSS is reached
# through nvmath (nvmath.sparse.advanced.DirectSolver) and is absent unless it
# is asked for, so a probe that only imports those three passes on an image
# that cannot factorise anything. The build probe therefore also loads the
# cuDSS shared library -- see the PROBE step in Dockerfile.gpu.

# cupy for the CUDA 12 runtime the A4000 nodes report. Not the [ctk] extra:
# that installs a second, version-drifting copy of the whole CUDA toolkit.
# Same pin the paper1 bench image measured.
cupy-cuda12x==14.2.0

# nvmath-python: the DirectSolver the GPU factorisation calls. 0.9.0 is what
# the Jetson worker's venv runs (read there by the lead, 2026-11-03); it is
# also the version whose tear-down (solver.free()) _CudssFactor.close() is
# written against.
#
# Pinned WITHOUT the [cu12] extra on purpose. The extra would pull cuDSS, but
# it also pulls nvidia-cuda-runtime-cu12 and cublas/cufft/cusolver/cusparse,
# i.e. a second CUDA runtime and solver set beside the base image's own CUDA
# 12.6. The extra is a convenience for a machine with no CUDA at all; this
# image has one, and two of them is how a build gets quiet version skew.
nvmath-python==0.9.0

# cuDSS, pinned explicitly because nothing else installs it.
#
# PyPI's requires_dist for nvmath-python 0.9.0 mentions cuDSS only as
#     nvidia-cudss-cu12==0.7.*; extra == "cu12"
# so a plain `pip install nvmath-python==0.9.0` installs NO cuDSS at all, and
# the first DirectSolver.factorize() is where that surfaces -- on the A4000,
# after the image has been built, pushed and deployed. 0.7.1.6 is the newest
# 0.7.1 wheel on PyPI; the Jetson runs the 0.7.1 line as a tarball at
# ~/cudss-0.7.1/lib, which is why that line and not 1.0.0.35.
nvidia-cudss-cu12==0.7.1.6

# cuda-bindings, pinned to the CUDA 12.x line.
#
# The A4000 smoke Job warned at import time:
#   "cuda-bindings was built for CUDA major version 13, but the NVIDIA driver
#    only supports up to CUDA 12"
# The solve was still exact (relative residual 1.0e-16 at n=20000), but that is
# luck, not a contract: an unpinned cuda-bindings floats onto the 13.x wheels as
# they publish, and the NEXT rebuild would get a different binding library
# against the same 12.6 driver. Pinning makes a rebuild reproducible.
#
# 12.9.9 is what the Jetson's gpu-venv and harness-venv actually run (read there
# 2026-11-03), so the A4000 and the Jetson use one binding library rather than
# two. Checked to resolve TOGETHER with the rest of this file, not in isolation:
# a --dry-run of these requirements against requirements.txt picks
#   cuda-bindings 12.9.9, cuda-core 0.7.0, cuda-pathfinder 1.8.5,
#   cuda-toolkit 12.9.2.0, nvmath-python 0.9.0, cupy-cuda12x 14.2.0
# with no conflict. The "built for CUDA 13" warning came from cuda-bindings
# being unpinned: pip's resolver picked the newest release (13.x). Any
# unpinned requirement here resolves to the latest on the next build, so
# every line in this file is pinned with ==.
cuda-bindings==12.9.9

# numpy/scipy come from requirements.txt, pinned there; cupy-cuda12x requires a
# compatible numpy and pip resolves against the already-installed one, so they
# are not restated here.
